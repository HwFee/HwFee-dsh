# 主题已知缺陷与修复记录

按发现顺序记录。每条都写明**症状、根因、为什么之前的实现看不出来**，以及**防止复发的测试**。

---

## 1. 令牌层完全没生效（冷启动）

**症状**：重启 DSH 后设置行在、样式表在，但 131 个颜色令牌一个都没应用。界面与宿主原样无异，控制台无报错。

**根因**：插件用 `ctx.get('theme')` 把主题服务当**可选服务**读取。`apply` 执行时主题服务尚未注册，读到 `undefined`，桥接器缓存了这个"不可用"结论并**永久放弃**。而 `inject` 只声明了 `['slots']`，Cordis 因此没有把这个插件的激活排到主题服务之后。

**为什么之前看不出来**：开发期用 HMR，主题服务早已存在，`ctx.get` 总能拿到。只有冷启动才暴露。

**修复**：
- `inject` 声明为 `['theme', 'slots']`（硬依赖）
- 桥接器不再锁死，服务晚到就下次重试

**防复发测试**：`test/bridge.test.mjs` — 断言 `inject` 必须含 `theme`；断言"服务晚到必须补上"；断言缺席时不抛错也不锁死。

## 2. 代码块黑底黑字（完全不可读）

**症状**：亮色主题下代码块底色近黑，文字也是深色，整块看不见。截图见开发记录。

**根因**：主题把 `.md-code-block` 强制成 `#0d0d0c` 深色底，指望"代码块在明暗下都是深的"（CDS 的 §8.5 主张）。但宿主的语法高亮是 **Shiki `css-variables` 模式**，每个 token 的颜色由 `style: { color: e.color }` 写成**内联 style**：

```js
function xR(e){const t={color:e.color}, ...}
...
u.jsx("span",{style:r.style, children:r.text})
```

内联 `color` 是任何样式表都改不了的。宿主的 `shiki.css` 声明的 `--shiki-token-*` 变量，与这条渲染路径实际使用的变量名**对不上**，所以覆盖它们也无效。结果：底色被我改了，文字色没跟着改。

**修复**：放弃"强制深色"，让代码块**跟随配色模式**。亮色用 `#f7f7f5`，深色用 `#0d0d0c`，与 Shiki 的明暗令牌组始终成对。CDS 的暖意改由圆角、发丝边框、banner 材质承载，不再靠反转语法色。

**代价**：放弃了 CDS 最具辨识度的"亮色下代码块也是深色"这一条。这是**受宿主渲染机制限制**，不是品味取舍。

**防复发测试**：`test/css.test.mjs`
- 亮/暗两条规则必须存在且底色不同
- 禁止在代码块规则里写死字面 `color`
- 禁止再出现 `--shiki-token-*`（那条路走不通）

## 3. 外观选择器"跟随系统"看着没选中

**症状**：设置 → 通用 → 外观，三个方块里"跟随系统"实际是当前值，但视觉上和未选中的白卡片几乎无差别，用户以为没选中任何一个。

**根因**：宿主用
```css
.selected { background: var(--dsw-alias-bg-module-platform);
            border-color: var(--dsw-static-neutral-bluish-400) }
```
- `border-color` 指向 **`--dsw-static-*` 静态调色板**，主题只覆盖 alias 层，从不碰静态层 → 边框仍是宿主冷蓝
- `bg-module-platform` 在亮色下是 `#f7f7f5`，与未选中的纯白卡片仅差 2 个色阶

**修复**：在 `[data-slot="settings.general.item"]` 作用域内，用强调色重写选中态（边框 + 12%/18% 填充），并保留 `:focus-visible` 焦点环作为第二重线索。

**防复发测试**：`test/css.test.mjs`
- 选中态必须有可见边框与填充
- 禁止依赖 `--dsw-static-*`
- 切换强调色预设时，选中态颜色必须跟着变
