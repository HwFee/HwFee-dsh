3. Why this mark

Why this shape. The first design was a three-track slider triptych — and the host's own IconPersonalizationOutlineMedium, the glyph for the 插件 entry, is also three tracks with round knobs. Two entries in one nav column showed the same sliders, which the user reported twice. That motif belongs to 插件 now. The replacement is two nested rounded frames: outer surface, inner shape, equal gap, tighter inner corner — the 同心圆角 relation this theme applies to the menu material, and the same two-surface idea as the plugin's own list artwork.

Why it cannot be confused. Measured against all five shipped nav glyphs (gear, sliders, knot-ring, database cylinder, person): every one is built from paths and circles — no rectangles at all across all five. A concentric pair of axis-aligned rounded rectangles appears in none of them.

Rejected candidates, each rendered at the real 16px rung on both palettes: a palette / swatch-fan (two offset chips collapsed into the host's “copy file” glyph; three chips read as dice); a 2×2 swatch grid (read as the app-launcher grid); a three-circle palette (read as the “users” glyph above).

4. How it gets there

The host's navIcon(id) is a hardcoded if-chain that ends in the gear for any id it does not know, so a slot registration cannot supply an icon. The plugin therefore finds the nav button structurally — the settings dialog is [data-shortcut-modal="settings"], the entry is the button whose label span equals our section label — inserts this SVG (marked data-cds-appearance-icon) before the host's own, and hides the host glyph with an inline display: none. Both mutations are undone on dispose; a host whose nav is missing or renamed keeps its own gear untouched.
